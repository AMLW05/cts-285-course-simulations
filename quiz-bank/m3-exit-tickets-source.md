## QUIZ: cts285-user-story-exit-ticket | Exit Ticket — From Requirement to User Story

@attempts: -1
@shuffle: true
@points: 1.0

> Five questions on turning a validated requirement into product work. You may retake this. Feedback appears on every option, so read the explanation even when you answer correctly.

### Q1. Which story keeps a real user in the seat?

- [x] As a teacher, I want to see which problem types a class struggles with so that I can plan the next lesson.
  - FB: Correct. A real person, a capability they need, and a reason that stays true even if the feature is built differently.
- [ ] As a product owner, I want a reporting feature so that teachers have reports.
  - FB: The product owner is not who receives the value. The "so that" restates the "I want", which is the reliable tell.
- [ ] As a database, I want to aggregate results so that queries run efficiently.
  - FB: Systems do not want things. When the actor is a component, the story has slid into design.
- [ ] As a teacher, I want better insight into student performance so that outcomes improve.
  - FB: Useful — right seat, real need. "Better insight" and "outcomes improve" are both undefined, so nobody could tell when this was done.

### Q2. Ship it as one story, or split it? "As a learner, I want to practise addition, subtraction, multiplication, and division so that I improve at arithmetic."

- [x] Split — four operations is four stories.
  - FB: Correct. Count the children under "I want". More than one and it is an epic, whatever the sentence looks like.
- [ ] Ship — it names one learner and one goal.
  - FB: One learner, yes. One goal, no. "Arithmetic" is doing the work of hiding four capabilities.
- [ ] Split into practice mode and results mode.
  - FB: Useful — a real axis, and the wrong one here. Nothing in the story is about results; the four operations are what is bundled.
- [ ] Ship — the original DataMan supported all four, so it is one feature.
  - FB: What the 1977 device did tells you the scope of the product. It does not tell you the size of a unit of work for a team.

### Q3. A story says a learner receives feedback after answering. Which is an acceptance criterion?

- [x] Feedback appears without the learner navigating away from the problem.
  - FB: Correct. Observable, testable, and silent about how it is built.
- [ ] Feedback appears in a modal dialog styled with the course palette.
  - FB: Too early. Modal and palette are design decisions that may be made later and are not the condition for done.
- [ ] Feedback is generated by a function named `check_answer`.
  - FB: Too early — an implementation detail. A criterion describes what the learner experiences, not what the code is called.
- [ ] Feedback is helpful and age-appropriate.
  - FB: Both matter and neither is testable as written. Two people would disagree about whether it passed.

### Q4. Given a learner has submitted a correct answer — which Then can a team actually verify?

- [x] Then the answer is marked correct and the next problem becomes available.
  - FB: Correct. Two observable conditions, both checkable in a single pass.
- [ ] Then the learner is rewarded appropriately.
  - FB: "Appropriately" moves the entire judgment into the tester's head. The original device flashed its display, which is a decision somebody made.
- [ ] Then the learner's confidence increases.
  - FB: A real design goal and not a Then. You cannot observe confidence at the moment of a keypress.
- [ ] Then the score is written to the database.
  - FB: Useful — perfectly verifiable, and it is a different requirement. Storage is not what this story promised the learner.

### Q5. A story in the backlog traces to no requirement in `docs/requirements.md`. What is the right move?

- [x] Ask what evidence supports it before it is sized or scheduled.
  - FB: Correct. An untraceable story is a preference until somebody establishes otherwise. That is a reason to ask, not a reason to bin it.
- [ ] Add a matching requirement to the register so the trace exists.
  - FB: Too early. Backfilling the register to justify a story you already like is exactly how an assumption becomes a requirement.
- [ ] Delete it — untraced work does not belong in a backlog.
  - FB: Useful instinct and too fast. It may be a real need nobody wrote down, which is a gap in the register found honestly.
- [ ] Leave it. Traceability matters for requirements, not for stories.
  - FB: Traceability is what lets you answer "why does this exist" in week nine, when the person who asked for it has forgotten.
