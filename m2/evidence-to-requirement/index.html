From Evidence to a Requirement

You have gathered evidence. Now the analyst has to convert that evidence into language a product team can understand, evaluate, and later turn into product work.

MLO 2.3 — Translate stakeholder and system evidence into clear, testable functional and non-functional requirements.
PatternControlled PracticeDataManQuality Check

A Good Requirement Has a Job

A requirement should help the team answer three questions:

  • What must be true?
  • Why does it matter?
  • How could we tell whether it has been satisfied?
Caution: In this module, you are defining the requirement—not the user story, task, interface, database, or code. Those decisions come later.

Use This Translation Pattern

1. EvidenceWhat did the source, stakeholder, or observation actually show?
2. NeedWhat problem, capability, or condition does that evidence reveal?
3. RequirementWhat must the system do or satisfy?
4. CheckCould a team later verify whether this requirement is met?
Controlled Practice

Separate the need from the proposed interface

Evidence: Employees report that they sometimes submit the wrong version of a form because multiple versions appear in search results.

Need: Employees need a reliable way to identify and access the current approved form.

Which statement works better as the requirement?

Weak requirement. It jumps to a specific interface choice before the team has established that the homepage is the right implementation.
Stronger requirement. It describes required behavior without locking the team into one interface solution.
Apply the Pattern to DataMan

Translate the original Answer Checker evidence

Evidence: In the original Answer Checker, DataMan allows a learner to enter a math problem and answer, indicates whether the answer is correct, and reveals the correct answer after repeated incorrect attempts.

Need: Learners need immediate feedback while practicing arithmetic.

Which statement is the strongest functional requirement?

Not yet. A hint system may be considered later, but this evidence does not establish that implementation.
Supported. This is clear, functional, observable, and tied directly to the evidence and learner need.
Still an open question. The manual gives evidence about the original three-attempt behavior; elicitation determines the modern requirement.
Open question: Should the 2026 version preserve the same three-attempt behavior, or should that interaction be redesigned? The manual gives evidence; elicitation determines the modern requirement.
Quality Check

Test a requirement before it enters the register

Use the same five checks from the course:

  • Clear: Would another team member interpret it the same way?
  • Necessary: Can you connect it to evidence, a need, or a project constraint?
  • Testable: Could the team later determine whether it was satisfied?
  • Solution-neutral enough: Does it avoid prescribing implementation unless the implementation itself is truly constrained?
  • Atomic enough: Is it focused on one main capability or quality rather than several unrelated ideas?

Inspect the examples

Weak: “The system must be modern, fast, secure, and fun for kids.”

This combines several vague qualities and provides no measurable condition. Break it apart and elicit what each term means.

Weak: “The system must use Flask and PostgreSQL so student work is saved.”

The need appears to be persistence of student work. Flask/PostgreSQL are implementation choices unless the project has explicitly constrained the technology.

Stronger: “The system must preserve a learner's saved practice data between authenticated sessions.”

This states observable required behavior while leaving implementation choices for later design work.

Hand-Off to Scrum

Requirements define what must be true about the system. In Module 3, the Product Owner and development team will translate approved requirements into user stories, acceptance criteria, estimates, and prioritized backlog work. A weak requirement creates weak product work downstream.
